# Windows / VS Code and local HTTPS deployment

## Local prototype
Use Python 3.12+, open the extracted folder in VS Code, and follow README.md. The local `runserver` binds only 127.0.0.1. Local HTTP is a development convenience and must not be exposed to students. SQLite is for development; its write locks do not validate the PostgreSQL concurrency guarantees.

## Final lab topology
Student phone/laptop → dedicated exam access point/VLAN → approved server interface → HTTPS reverse proxy (443) → Waitress on 127.0.0.1:8001 → MySQL or PostgreSQL on a private interface. The expiry worker uses the same database and configuration. No public tunnels or port forwarding. Do not run both an unrestricted HTTP listener and the exam HTTPS listener.

1. Install MySQL 8.0.11+ or PostgreSQL and its command-line tools. Create an empty `secure_exam` database (`utf8mb4` for MySQL). Use a migration owner for migrations; use a separate runtime `exam_app` login with only needed table permissions. Deny UPDATE/DELETE on audit and score revision tables. The schema triggers additionally reject those operations and published-quiz edits. Never make the application login a database superuser. Tests need a separate database account permitted to create temporary test databases and must never target production data.
2. Copy `.env.example` to `.env`; generate independent keys using `secrets.token_urlsafe(48)` for DJANGO_SECRET_KEY and `Fernet.generate_key().decode()` for EXAM_ENCRYPTION_KEY. Keep keys outside source control. Set DB values, BASE_URL, allowed host, SMTP credentials, and proxy settings. DEBUG must be 0.
3. Pick a stable hostname/IP reachable from student devices. Configure local DNS or hosts entries. A QR pointing to localhost opens the student's own device, not your server. Create a certificate for the exact DNS name and, if used, server IP. For a small controlled lab, install a local CA (for example mkcert) on the server and its public root certificate on authorized devices through the device's normal trust settings. Keep the CA private key only on the issuing machine. Never tell students to bypass browser warnings.
4. Configure Nginx using `nginx.conf.example` as a starting point. Replace every example address/path. Configure one approved interface listener, the actual exam subnet, TLS paths, and a local static directory. The proxy overwrites forwarding headers; the application only trusts the configured loopback proxy. Scan invitations and activation links carry bearer tokens in URL query strings. Disable access logs for these routes or use a carefully reviewed log format that excludes query strings.
5. Apply migrations with the migration account: `python manage.py migrate`. Collect static files: `python manage.py collectstatic --noinput`. Restore runtime database credentials. Run `python manage.py check --deploy`; resolve warnings before a real exam.
6. Start `python serve_production.py` behind the proxy. Start `python manage.py finalize_exams` in a separate supervised process. On Windows use Task Scheduler or a service manager configured to restart on failure. Set the working directory and protected environment explicitly. Do not use the development server for the final exposed exam.
7. In Windows Defender Firewall, inspect existing allow rules first. Restrict the HTTPS listener's program/port to the actual exam interface, local server IP and remote subnet. Keep default inbound blocking. Remove or narrow any existing broad rule that exposes this listener on other adapters. Do not add a global deny that overrides the intended allow rule. Block external access to application and database ports (MySQL 3306 or PostgreSQL 5432). Verify from both an authorized and an unauthorized device. Disable or separately constrain IPv6 listeners; the application rejects IPv6 sources not explicitly mapped by the selected profile.
8. Admin creates a named network profile containing the observed subnet and interface description. Teacher selects it at exam start. The server uses trusted connection source, not SSID, browser fields or arbitrary forwarded headers. Network profiles are not proof of physical presence.

## Hotspot / university Wi-Fi
A phone hotspot is only suitable if device-to-device traffic works and the laptop and student devices can reach each other. Test client isolation, DHCP address changes, sleep/battery settings, device capacity, IPv6 and VPN routes. University Wi-Fi needs IT-approved VLAN/firewall rules; a shared university public IP cannot prove classroom presence. Run on the teacher laptop, not the phone. Changing Wi-Fi must never pause or reset the exam deadline.

## Certificate / key operations
Track the certificate expiry date and renew before expiry using the same trusted CA or a reviewed CA rollover. Test renewed certificates on each target device. Protect private keys with OS ACLs. For exam encryption-key rotation, stop application/worker, take an encrypted backup, decrypt all ExamSession.invitation_cipher values with the old key, encrypt them with the new key in one maintenance transaction, verify samples, replace the environment key and restart. Do not rotate during an exam. Keep old keys with backups for their retention period. A SECRET_KEY rotation revokes authenticated sessions; schedule it outside exams.

## Operational acceptance
Synchronize server UTC before opening the exam; do not change its clock while live. Check database disk space, TLS validity, worker process health and last successful backup. Capture errors without request bodies or secrets. Investigate repeated denial/login events in the audit UI. If service/database fails, show save failures and preserve received answers. A replacement exam needs an explicit new quiz and audit trail. Never delete attempts to allow a retake.

## Legacy activation links
Activation links are retained only for an existing pending account or the initial administrator created by `bootstrap_admin`; they are not used to provision new students. Open such links as top-level pages in a regular browser. Message previews, sandboxed frames and some embedded webviews can submit with the opaque `Origin: null`; Django correctly rejects those POSTs even when the form includes its CSRF token. The application uses `Referrer-Policy: same-origin`: same-origin form posts retain the origin/referrer information Django needs, while cross-origin requests still receive no referrer. Activation links are redirected to a clean URL before the form is rendered, so the bearer token is not included in that referrer. Do not add `null` to `CSRF_TRUSTED_ORIGINS`, disable CSRF, or bypass browser security. Activation ends with ordinary username/password login and does not require OTP/MFA.
